# אפיון: מחלקת "אישורים חריגים" — 28.07.2026 (גישה מפושטת)

מחלקה חדשה בפרויקט "היכל החתם סופר" (Next.js + Supabase, פרודקשן חי).

## הרעיון

אנשים שאינם צאצאים (נכדים), שהמנהל מכניס ומאשר להם להגיש בקשות. הם עובדים **בדיוק כמו מוטב רגיל** — אותם טפסים, בקשות, פורטל, ניהול — **ההבדל היחיד: אין להם סדר דורות** (הם לא צאצאים, ולכן לא צריכים את כל עניין הייחוס).

## הגישה (החלטת המשתמש): דגל על הקיים — לא טבלה נפרדת

- שדה חדש `is_special boolean default false` על `beneficiaries`.
- אדם חריג = רשומה רגילה עם `is_special=true`, בלי `lineage_*`.
- **כל הבקשות/טפסים/פורטל/ניהול עובדים מיד** — הם ממילא מקושרים ל-`beneficiary_id` בלבד ואינם תלויים בסדר הדורות.
- ההבדל היחיד: כשהאדם `is_special` — **מדלגים** על כל מה שקשור לדורות.

**היתרון:** מעט קוד, פחות תחזוקה, מהיר. כמעט הכל כבר קיים.

---

## מה צריך לבנות

### 1. מיגרציה (קטנה)
```sql
alter table public.beneficiaries add column if not exists is_special boolean not null default false;
create index if not exists beneficiaries_special on public.beneficiaries (is_special) where is_special = true;
```
`default false` → כל הרשומות הקיימות = רגילות. כלום לא נשבר.

### 2. דילוג על סדר הדורות כשהאדם חריג

בכל מקום שנוגע בייחוס — לדלג כש-`is_special`:
- **טאב "עץ הדורות"** בכרטסת — מוסתר לחריגים.
- **שער אישור המשפחה** (`FamilyApprovalGate`) — לא חוסם לחריגים.
- **`deep_review` ברישום** (`public-register`) — לא חל על חריגים (אין להם דורות).
- **חלונית ההתראה** של סדר דורות — לא קופצת לחריגים.

### 3. הכנסת אדם חריג (ניהול)

- הרישום הידני הקיים (`app/admin/beneficiaries/new` → `BeneficiaryForm`) כבר עושה את רוב העבודה.
- להוסיף בטופס: מצב "אדם חריג" (checkbox/toggle) שמסמן `is_special=true` ו**מסתיר את שדות סדר הדורות** בטופס.
- admin-only (הכפתור "אדם חריג" עטוף `AdminOnly`).

### 4. טאב בתפריט — צפייה נפרדת בחריגים

- פריט `NavItem` חדש ב-`Sidebar.tsx` ("אישורים חריגים"), עטוף `isAdmin`.
- דף `app/admin/special-approvals/page.tsx` — משתמש **חוזר** ב-`BeneficiariesTable` הקיים, מסונן `is_special=true`. כך אין שכפול — אותה טבלה, אותם מסכי פרטים.
- הצאצאים הרגילים (הרשימה הראשית) מסוננים `is_special=false` (או null) — כדי שהחריגים לא יופיעו שם.

### 5. הגשת בקשות

- **אין מה לבנות** — כל הבקשות (לידה/הלוואה/סיוע) כבר עובדות דרך `beneficiary_id`. אדם חריג מגיש בדיוק כמו כל מוטב, בפורטל או דרך המנהל.
- לוודא ששערי המחלקות (department gates) חלים גם עליהם (סביר שכן, ללא שינוי).

## סדר ביצוע

| שלב | תוכן | DB |
|-----|------|-----|
| 1 | מיגרציה `is_special` + סינון הרשימה הראשית (החריגים לא מופיעים בצאצאים) + טאב בתפריט + דף מסונן | מיגרציה |
| 2 | טופס: מצב "אדם חריג" (מסמן is_special, מסתיר שדות דורות) | לא |
| 3 | דילוג על ייחוס בכרטסת (טאב דורות, שער משפחה, התראות) לחריגים | לא |

**המלצה:** שלב 1 קודם — נותן ערך מיידי (אפשר להכניס ולראות חריגים בנפרד). שלבים 2-3 משלימים את החוויה.

**סיכון כולל:** נמוך. מיגרציה בטוחה (`default false`), שימוש חוזר בקוד קיים, בידוד לוגי דרך הדגל.
